## ISSUE-001 — Cost accounting is inflated ~100,000× (config + dual-unit interpretation)

**Severity:** Critical
**Category:** Functional / Cost
**Reproducible:** Yes

### Evidence

A single `agnes-2.0-flash` call (286 prompt + 20 completion = 306 tokens) billed **$25.72**:

- `_meta.cost` in the chat response: `25.72`
- `/admin/api-keys` quota for the key: `monthly_cost_used: 25.82` after one call (limit $10 → immediately over quota)
- `/admin/costs/summary`: `cost_usd: 3710.56` for 183,568 tokens across 446 requests
- Control-panel Cost Analysis page: **"总成本 (近7天) $3504.58 · 平均单次成本 $12.61"**
- Control-panel Quota page: admin key shows `$2224.84 / $5000.00`

### Root cause

`config.yaml` prices `agnes-2.0-flash` and `deepseek-v4-flash`/`-pro` at `prompt: 0.02, completion: 1`:
```yaml
pricing:
  agnes-2.0-flash:
    prompt: 0.02
    completion: 1
```
The **same config field is interpreted with two different units** depending on the code path:

1. `aigateway-core/.../route/metrics/costing.py:74` — `amount = prompt_tokens * prompt_price + completion_tokens * completion_price` → treats `0.02` as **$0.02/token**. (286×0.02 + 20×1.0 = $25.72 ✓ matches observed cost)
2. `aigateway-core/.../route/model_resolution/model_router.py:528` — `price = float(prompt_price)` stored as `ModelConfig.price_per_request` → treats `0.02` as **$0.02/request** (flat).
3. `aigateway-core/.../route/bridge/_litellm_bridge_impl.py:553-554` — passes the value to litellm as `input_cost_per_token` / `output_cost_per_token` → treats `0.02` as **$0.02/token** (litellm's own cost model).
4. The **control panel Models page displays the pricing as "$0.02 / $1 每 token"** — explicitly labeling it per-token.

The builtin fallback table (`_litellm_bridge_impl.py:1341`) lists `agnes-2.0-flash: 0.0000005` (i.e. $0.50/1M tokens — a realistic per-token rate), confirming the configured `0.02` is **~100,000× too large** for a per-token interpretation.

### Impact

- Every API key with a realistic monthly cost limit (e.g. $10) is exhausted by a single short call. Quota enforcement then blocks all subsequent calls with 429 `quota_exceeded_monthly_cost`.
- Admin cost dashboards show wildly inflated totals ($3710 for ~183K tokens), making cost monitoring useless and misleading capacity planning.
- The `price_per_request` path (model_router) and the per-token path (costing.py / litellm) disagree, so routing cost-based decisions use a different number than quota enforcement.

### Repro
```bash
# After login + creating a $10-limit key:
curl -sS $B/v1/chat/completions -H "Authorization: Bearer $K" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"hi"}],"max_tokens":20}'
# → response _meta.cost ≈ 25.7; key now over quota
```

### Verification test
A regression test should assert: for a 306-token agnes-2.0-flash call, `estimate_cost_from_pricing` returns a value on the order of $0.0001–$0.001 (per builtin table), NOT $25.7. The costing path and the `price_per_request` path must agree on units.

## ISSUE-002 — Image draft generation hangs forever at 10% / status=running

**Severity:** Critical
**Category:** Functional / Image pipeline
**Reproducible:** Yes (observed twice)

### Evidence

In the control-panel Chat page, selecting the image flow (default "自动选择" + a Chinese prompt like "画一只可爱的猫") creates a draft and the UI shows "🎨 图片 · draft · ComfyUI 正在生成草稿预览…" — which **never resolves**. After 90+ seconds the preview is still "running."

- `GET /admin/draft/{id}/preview` returns **202 Accepted** with `{"status":"running","progress":0.1}` indefinitely. The frontend polls it dozens of times.
- `GET /admin/draft/{id}`: `"status":"running"`, `"progress":0.1`, **`"comfy_prompt_id": null`**, `"gpu_seconds":0.0`.
- `GET /admin/comfyui/status`: queue `{"running":0,"pending":0}` — **the job was never submitted to ComfyUI**.
- ComfyUI container logs show no prompt received, no errors — idle.
- The request log records this stuck call as **HTTP 200, 5360ms** (a success, despite never producing output).

### Root cause (inferred)

The gateway's draft workflow marks the draft `running` at progress 0.1 but never dispatches a prompt to ComfyUI (`comfy_prompt_id` stays null). The likely upstream cause: **`/admin/gpu/status` reports the gateway's own GPU as `available:false, error:"gpu_status_unavailable"`** (see ISSUE-004). If the draft scheduler gates dispatch on the gateway-side GPU status (rather than ComfyUI's reported availability), it would never submit the job. ComfyUI itself is healthy and reports the Tesla T4 with 15.5GB free.

This matches the prior "console chat draft preview bug" memory ([[console-chat-draft-preview-bug]]) — still present on main.

### Impact

- Image generation in the console is completely broken: no image is ever produced.
- The user sees a perpetual spinner with no error, no timeout, no fallback.
- The request is logged as 200 success, masking the failure.

### Repro
1. Login to control panel → Chat.
2. Type an image-shaped prompt (e.g. "画一只可爱的猫") + send.
3. Observe "ComfyUI 正在生成草稿预览…" that never completes.
4. `curl /admin/draft/{id}` shows `comfy_prompt_id: null`, `progress: 0.1` indefinitely.

### Verification test
A regression test should assert that after a draft is created, within a bounded time `comfy_prompt_id` becomes non-null (job submitted to ComfyUI) OR the draft transitions to `failed` with an error — never hangs at `running` with null prompt id.

## ISSUE-003 — Gateway GPU status reports unavailable while ComfyUI sees the GPU fine

**Severity:** High
**Category:** Functional / GPU scheduler
**Reproducible:** Yes

### Evidence

`GET /admin/gpu/status`:
```json
"gateway": {
  "available": false,
  "device": null,
  "allocated_bytes": 0,
  "torch_initialized": false,
  "cuda_disabled": false,
  "error": "gpu_status_unavailable"
},
"comfyui": {
  "available": true,
  "gpu": {"name": "cuda:0 Tesla T4 ...", "vram_free": 15527051264}
}
```

### Impact

The gateway cannot see the CUDA device that ComfyUI successfully uses. Likely related to ISSUE-002 (image draft hang) — if the draft/GPU scheduler gates on the gateway-side status, the job never dispatches. Even if unrelated, the `gpu_status_unavailable` error is a real defect on a box that has a working Tesla T4.

### Repro
```bash
curl -sS -b cookies http://127.0.0.1:8000/admin/gpu/status | jq .data.gateway
```

### Verification test
On a host with a CUDA GPU and ComfyUI reporting it, `/admin/gpu/status` `data.gateway.available` should be `true` with a non-null device, not `error: gpu_status_unavailable`.

## ISSUE-004 — Upstream streaming failure mapped to HTTP 200 + success terminal marker

**Severity:** High
**Category:** Functional / Streaming protocol
**Reproducible:** Intermittent (upstream-driven; observed 1x in early runs, not on demand)

### Evidence

One streaming `POST /v1/chat/completions` (stream=true) returned:
```
HTTP/1.1 200 OK

data: {"error": {"code": "upstream_timeout", "message": "All stream models failed: "}}

data: [DONE]
```

The body is an **error event** but the HTTP status is **200** and the stream ends with the **`data: [DONE]` success terminal marker**.

### Impact

This violates two product contracts from CLAUDE.md:
- "SSE code must … emit at most one terminal marker. **Never report a successful terminal event after an upstream failure.**"
- "Streaming and non-streaming paths must have parity for … error mapping."

A client parsing only HTTP status + DONE will treat this as success; the actual error is buried in a data line that not all clients inspect. Retry logic keyed on HTTP status will not retry.

### Repro
Intermittent — depends on the agnes upstream timing out on the stream path. A deterministic test would mock the bridge to raise on `completion_stream` and assert the endpoint returns 5xx (or an error terminal, NOT `[DONE]`).

### Verification test
Mock the streaming bridge to fail; assert response is NOT 200-with-`[DONE]`. It must be a non-2xx status, or an SSE stream that ends with an error marker and no `[DONE]`.

## ISSUE-005 — Low max_tokens returns empty content (reasoning eats the whole budget)

**Severity:** Medium
**Category:** Functional / Chat
**Reproducible:** Yes (deterministic)

### Evidence

`max_tokens=10` on `agnes-2.0-flash` returns:
```
content: "" (empty)
reasoning_content: "The user wants me to say hi. Simple greeting"
finish_reason: "length"
usage: completion_tokens=10, reasoning_tokens=10, text_tokens=0
```

The model's reasoning consumes the entire `max_tokens` budget, so `content` is empty and `finish_reason` is `length`. Non-stream and stream both behave this way.

### Impact

Clients sending a low `max_tokens` (a common pattern to limit cost/latency) get a silent empty reply with no error — they must inspect `reasoning_content` and `finish_reason` to understand why. Not strictly a gateway bug (the upstream model spends tokens on reasoning), but the gateway passes it through without warning, and combined with ISSUE-001 the user pays ~$0.20 for an empty reply.

### Verification test
Document the contract: when `finish_reason=="length"` and `text_tokens==0`, the response should either surface a warning or document the reasoning-budget behavior. At minimum, a test asserting the observed behavior so it isn't silently changed.

## ISSUE-006 — ConvCompressorPlugin re-initialized on every request (log spam)

**Severity:** Low
**Category:** Performance / Operational
**Reproducible:** Yes

### Evidence

Gateway logs show, repeated on every request:
```
ConvCompressorPlugin 已初始化: summary_model=agnes-2.0-flash, max_history=20, max_token_limit=4000
Unstructured 未安装，回退到多库实现
```
These appear before each `GET /health` 200 log line — i.e. the plugin re-initializes per request (or at least per health check), rather than once at startup.

### Impact

Unnecessary per-request work and log noise. "Unstructured 未安装" is logged on every request even though the fallback is stable. Not user-visible, but degrades log signal and may add per-request latency.

### Verification test
Assert the plugin's `__init__`/init message is emitted once during lifespan startup, not once per request.

## Top 3 things to fix

1. **ISSUE-001 (cost accounting):** Decide the unit for `pricing.prompt`/`completion` (per-token is the litellm/costing.py interpretation and what the UI shows; per-request is model_router's).
